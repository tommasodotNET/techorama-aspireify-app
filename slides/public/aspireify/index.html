Aspireify

/ə-ˈspī-ər-i-ˌfī/ verb

To add Aspire orchestration to an existing app stack so it becomes easier to run, observe, configure, and deploy.

Usually involves connecting services, dependencies, environment variables, cloud resources, and developer workflows into one cohesive Aspire-powered app model.

Example

“We Aspireified our app so the API, frontend, database, cache, and worker all start from one place.”

Related forms

Aspireified adj. — an app orchestrated by Aspire

Aspirification noun — the process of Aspireifying a stack

The whole talk in one word. Aspireify = take something that already exists and add Aspire to it. No rewrite, no new framework, no migrating your deployments. By the end of the hour we want you to believe you can do this to your own app this afternoon.

Dev loop

Deployments

Two halves of the same problem. Locally: onboarding takes days, adding a service means touching five files, and agents are guessing. Deploy side: the topology lives in someone’s head and a pile of YAML. Keep this fast — the demo is where we prove the fix.

The one-liner. Emphasize “any”: frontends in JS, APIs in .NET, Python, Go, Java — containers or executables. And “no rewrites”: Aspire wraps what you already have.

Four pieces you’ll see in the demo

AppHost

The code-first map of your app: every service and how they connect. C# or TypeScript.

Integrations

100+ packages for databases, caches, queues, AI and clouds. Opinionated by default.

Dashboard

Logs, traces, metrics and resources in one place — plus an MCP server for agents.

CLI

One agent-ready control plane to create, run and deploy the whole thing.

Don’t teach these in depth — the demo does that. Just name them so people recognize them on screen: AppHost is the map, integrations are the building blocks, the dashboard is where you see it all, and the CLI drives it (and gives your coding agent context).

CLI cheat sheet

Install: get.aspire.dev

CommandWhat it does
aspire initAdd an AppHost to an existing app
aspire newStart a new app from a template
aspire addSearch for and add an integration
aspire runRun the AppHost, every resource and the dashboard
aspire start --isolatedRun in the background on random ports (worktrees, agents)
aspire ps / stop --allList or stop running AppHosts
aspire publish / deployGenerate deployment assets, or deploy directly
aspire doctorCheck your environment is ready
Backup slide — show it if someone asks “what was that command?” or leave it up during Q&A. Every command is also available from the Aspire VS Code extension.

Your next hour

How Aspireified do you want to get?

If I reformatted my machine today, what would it take to run my app?

What do new teammates always get stuck on?

How much of my .env is service wiring vs. real secrets?

Which dev scripts belong in the AppHost as commands?

Do I work across worktrees and need isolated ports?

Which parts of my app should be able to run on their own?

Give people homework. Start with the simplest vertical slice — even just running the frontend — and grow from there. These questions tell you how far to take it. Tip from Oslo: a coding agent with the Aspire skills can do a surprising amount of the first pass.

“But what about production?”

Keep your deployments

Use Aspire just for the dev loop. Your pipelines don’t have to change.

A model, not a runtime

The AppHost describes your app. It isn’t something you run in prod.

Publish for any target

Generate Docker Compose, containers and cloud assets — or deploy with the CLI.

Hand over real artifacts

Pre-built containers and Compose files your ops team can test end to end.

The question we always get. Short answer: adopting Aspire for dev is zero-risk for prod. When you’re ready, the same model can generate deployment assets. Note: the dashboard can be deployed, but it’s a dev tool, not a production monitoring solution.
